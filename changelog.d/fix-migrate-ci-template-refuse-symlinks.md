### Security

- **`migrate`, `rule-pack init`, `coverage setup` and `ci-template gitlab --vendor` no longer write through a symlink that leaves the project.** A cloned repository could commit a file or directory that one of these commands writes as a symlink to a path outside the project. `fallow migrate` then created the outside file with the migrated config when `.fallowrc.json`, `.fallowrc.jsonc` or `fallow.toml` was a dangling link. `rule-pack init` did the same for `rule-packs/team-policy.jsonc` or a linked `rule-packs` directory, and it added the `rulePacks` entry to an outside file that `.fallowrc.json` linked to. `coverage setup` wrote `setup.lock` and `setup.json` into a linked `.fallow` directory, and it wrote `docs/collect-coverage.md` through a link, so it could overwrite an outside file. `ci-template gitlab --vendor <dir>` wrote `ci/gitlab-ci.yml` and `ci/scripts/*.sh` through a link below `<dir>`, and with `--force` it also overwrote an existing outside file. These commands now stop with an error when the target, or a directory on the way to it, is a symlink that resolves outside the project or a dangling link. `migrate`, `rule-pack init`, `coverage setup` and `ci-template` exit with code 2. When only the config file of `rule-pack init` links outside the project, the command writes the pack, leaves the config unchanged and prints the `rulePacks` entry to add by hand. This is the check that `init` and `agent install` already use. A link that stays inside the project still works, and `migrate --dry-run` is not affected.
