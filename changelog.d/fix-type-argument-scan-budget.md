### Fixed

- **A long comparison chain or nested lists in JSX text, a template attribute or a script block no longer make the parse use gigabytes of memory.** In TypeScript the parser tries each `a<` of an expression as a list of type arguments, and reads the same bytes again when that fails. A flat chain such as `a<a<a<...<a` of 16 KB used about 2 GB, and nested lists that the scan before the parse did not see used memory until the run stopped. The scan now counts the bytes that the parser can read again, and a file past that budget gets the `source-nesting-too-deep` diagnostic and is not parsed. The scan also reads a JSX file as the parser does: quotes, comment openers and `)` in the text of an element are text. It reads a `/` after the `)` of an `if`, `while`, `for` or `with` header as a regex, and a `#!` line at the start as a comment. A template expression of a Vue, Svelte, Astro or Angular file, and a script block of a component, Astro or MDX file, now get their own scan, so their nesting is seen too. The prose of an HTML, MDX, Vue, Svelte or Astro file can hold a bare `<`, so the scan of the whole file does not apply the budget there. A scan of an unclosed string or regex on a long line no longer takes time that grows with the square of the line length. Real code stays far below these limits. The parse cache and the duplication token cache are rebuilt once.
