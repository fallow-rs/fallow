### Added

- **The GitHub Action and the GitLab template can run `fallow mutation`.** Set the input `mutation: true` (GitLab: `FALLOW_MUTATION: "true"`). The step runs before the analysis, with the changed lines of the pull request as the default scope and a `10m` time budget. The inputs `mutation-scope`, `mutation-time-budget`, `mutation-max-mutants` and `mutation-min-score` (GitLab: `FALLOW_MUTATION_SCOPE`, `FALLOW_MUTATION_TIME_BUDGET`, `FALLOW_MUTATION_MAX_MUTANTS`, `FALLOW_MUTATION_MIN_SCORE`) set the run. The existing sticky comment and the job summary get one "Mutation testing" section with the killed, survived, no-coverage and not-measured counts, the budget state, and the top survivors with a `fallow mutation inspect <id>` command. A partial run says "Partial run". Exit code 2 of the run fails the job with the error code and the message, after the comment. The step refuses a job that has the secrets of the base project and can run the code of a fork (on GitHub, each event other than `pull_request`, `push`, `schedule`, `workflow_dispatch` and `merge_group`; on GitLab, a fork pipeline in the target project), and it never passes `--allow-dirty`. The result cache goes through `actions/cache` and the GitLab job cache, with a key that covers the lockfiles and the runner config. A fork pull request never saves the cache. `fallow ci-template gitlab --vendor` also writes `ci/scripts/mutation.sh` and `ci/scripts/mutation_common.sh`.
