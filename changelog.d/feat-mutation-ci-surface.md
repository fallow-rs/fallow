### Added

- **The GitHub Action and the GitLab template can run `fallow mutation`.** Set the input `mutation: true` (GitLab: `FALLOW_MUTATION: "true"`). A `Resolve change scope` step (GitLab: an inline block) writes one root-relative diff first. Then the mutation run uses that diff, before the analysis, because the run refuses a dirty worktree. The default scope is the changed lines of the pull request, with a `10m` time budget. The inputs `mutation-scope`, `mutation-time-budget`, `mutation-max-mutants` and `mutation-min-score` (GitLab: `FALLOW_MUTATION_SCOPE`, `FALLOW_MUTATION_TIME_BUDGET`, `FALLOW_MUTATION_MAX_MUTANTS`, `FALLOW_MUTATION_MIN_SCORE`) set the run. `fallow report` renders the results (see the next entry). A failed `mutation-min-score` fails the job with exit code 1, and a tool failure of the run (exit code 2) fails it with exit code 2, after the comment. The step runs only for a job that cannot run the code of a fork with the secrets of the base project: on GitHub, the `pull_request`, `push`, `schedule`, `workflow_dispatch` and `merge_group` events; on GitLab, not a fork pipeline in the target project. It removes the CI tokens and the `GITHUB_*` file commands from the environment of the tests, and it never passes `--allow-dirty`. The result cache goes through `actions/cache` and the GitLab job cache, with a key that covers the lockfiles and the runner config. A fork pull request never saves the cache. With a fallow that cannot render the results, the gate still fails the job, and the job summary names the version that renders them. `fallow ci-template gitlab --vendor` also writes `ci/scripts/mutation.sh` and `ci/scripts/mutation_common.sh`.
