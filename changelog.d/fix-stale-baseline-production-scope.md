### Fixed

- **`fallow baselines prune` no longer removes valid entries of a baseline saved in another mode.** A prune on a file saved with `--production` or `--include-entry-exports`, in a run without that mode, removed entries that are valid in that mode and exited 0. A prune in production mode did the same to a whole-project file, also for `health` and `dupes` baselines. Prune now refuses such a file with `reason_code: "scope-mismatch"` and exit 2, leaves it byte-identical, and prints the command to use. `baselines prune` now accepts `--production` and honors `--include-entry-exports`, which it accepted and ignored. A file with no record of a mode that the run uses is refused too, so `prune --check` can exit 2 for a config-production user with an older file. To clear that refusal, review the findings and save the file again in that mode. `health` and `dupes` saves now record production mode for this guard.
- **`--fail-on-stale-baseline` now judges a dead-code baseline saved in the same mode as the run.** A job that armed the gate can exit 1 where it exited 0, when the file holds a stale entry. To clear it, run the prune command that the failure prints and commit the result. A run in another mode than the file no longer fails this gate: it exits 0 where it exited 1, and the gate status is `skipped`. The rule covers `--production`, `includeEntryExports`, and an issue-type filter that reports every category in the file, so a filter-only run can also exit 1 where it exited 0. The stale advisory can now appear on those same-mode runs without the gate. `change_scoped` and `scope_reasons` on `dead-code` now name what stops this run from judging the file, so `production` can appear on a run without `--production`. `health` and `dupes` gates stay inert in production mode, and the note says so. Thanks @Smrtnyk for the report.
