# Detection capabilities

Non-obvious implementation details for each detection feature. These are NOT discoverable from reading the code alone.

## Parser-level
- **HTML entry files**: `<script src="...">` (module and classic) and `<link rel="stylesheet" href="...">` / `<link rel="modulepreload" href="...">` create graph edges from HTML to referenced assets. Remote URLs skipped. HTML comments stripped before matching. HTML files exempt from unused-file detection.
- **JSX asset references**: lowercase intrinsic `<script src="...">` and `<link rel="stylesheet|modulepreload" href="...">` inside JSX/TSX files create `SideEffect` imports, mirroring the HTML parser. Only `JSXAttributeValue::StringLiteral` values are captured; expression containers (`href={expr}`) and capitalized React-style components (`<Script>`, `<Link>`) are ignored. Needed for SSR frameworks like Hono where layout components emit HTML via JSX. Combined with the web-root-relative resolver branch, `<link href="/static/style.css" />` correctly reaches sibling `static/style.css` files. See issue #105 (till's comment).
- **`html` tagged template asset references**: `` html`<script src="..."></script>` `` and `` html`<link rel="stylesheet|modulepreload" href="..."/>` `` inside any JS/TS file create `SideEffect` imports via the regex-based HTML asset scanner (`crate::html::collect_asset_refs`). Only the bare identifier tag `html` is matched — `css`, `sql`, `gql`, `styled.div`, and member/call expressions are deliberately ignored to avoid misreading unrelated tagged templates as HTML. Each template quasi is scanned independently, so an asset reference split across an interpolation boundary (`` html`<script src="${base}/app.js">` ``) is skipped rather than producing a garbled unresolvable specifier. Needed for SSR helpers like `hono/html`, `lit-html`, and `htm` where layout components emit HTML via tagged templates instead of JSX. See issue #105 (till's follow-up comment).
- **JSDoc `import()` type references**: JSDoc comments matching `import('./path').Member` inside `@param`, `@returns`, `@type`, `@typedef`, `@callback`, or other tag contexts are extracted as type-only imports. Supports single/double quotes, bare specifiers, parent-relative paths, union annotations with multiple `import()` expressions per comment, and nested member access (first segment wins). Side-effect-only `import('./types')` without `.Member` is recorded as `SideEffect` to keep the file reachable. Prevents false `unused-export` reports for types referenced only from JSDoc annotations in untyped JS files. Only `/** */` block comments are scanned (single-star `/* */` is not JSDoc). See issue #105 (till's comment).
- **Vue/Svelte SFC**: handles `>` in quoted attributes like `generic="T extends Foo<Bar>"`, `<script src="...">` external script support, HTML comment filtering. Template-visible import tracking: imports used only in markup (`{formatDate(x)}`, `utils.formatDate()`) are credited as used, preventing false unused-import/export reports. Vue credits only `<script setup>` bindings; Svelte excludes `context="module"` scripts from template visibility. Namespace member access in templates (`utils.formatDate`) tracked as member usage.
- **Vue/Svelte SFC `<style>` blocks**: `<style lang="scss">` and `<style lang="sass">` block bodies are scanned for `@import` / `@use` / `@forward` directives via the same regexes used for plain `.scss` files (issue #195 Case B). Plain `<style>` (no `lang`) and `<style lang="css">` are scanned for `@import` only. `<style src="./theme.scss">` external style references are extracted symmetrically with `<script src>` and emit a `SideEffect` import on the SFC. Each style-context import is tagged with `from_style: true` on `ImportInfo` so the resolver routes through the SCSS fallback chain (CSS-extension probe, partial convention `_filename`, include paths, node_modules) BEFORE the standard JS resolver. Without that routing, `./Foo` from a `Foo.vue` style block would resolve to the SFC itself (`.vue` precedes `.scss` in the resolver's extension list); the CSS-restricted probe selects the sibling `Foo.scss` instead. Languages other than CSS / SCSS / Sass (`postcss`, `less`, `stylus`) only have their `<style src>` reference seeded; their body syntax differs (e.g., Less `@import (reference)` modifier) and is out of scope.
- **Namespace destructuring**: `const { a, b } = ns` → member accesses. Rest patterns (`const { foo, ...rest } = ns`) → conservative whole-object use. Works with static/dynamic imports and require.
- **Node `child_process.fork()` entrypoints**: module-scope `fork()` calls emit `DynamicImportInfo` entries only when the callee is proven to come from `node:child_process` / `child_process`. Supported provenance forms are `import { fork }`, `import * as childProcess`, `const { fork } = require(...)`, and `const childProcess = require(...)`. Supported targets are local string/template literals without expressions, `new URL('./runner.js', import.meta.url)` bindings, and `path.resolve(filename, '../runner.js')` where `filename` is bound to `fileURLToPath(import.meta.url)` and `path` is from `node:path` / `path`. Unresolved identifiers, non-local specifiers, computed templates, nested shadowed calls, and unrelated `fork` functions are ignored. See issue #638.
- **Unused import bindings**: via `oxc_semantic` scope-aware symbol analysis. Dead imports don't count as references, improving unused-export precision.
- **TypeScript overload dedup**: `export function foo(): void; export function foo(x: string): string;` treated as single export
- **Import-then-reexport pattern**: `import { X } from './a'; export { X };` is detected as a re-export (semantically equivalent to `export { X } from './a';`) instead of a local export. Without this, the bottom export collides with the original in duplicate-export detection and is never reached by re-export chain propagation. Handles renames on either side (`import { X as Foo }; export { Foo }` or `import { X }; export { X as Y }`), default imports (re-exported with `imported_name: "default"`), and mixed local + re-export in one statement. Order-sensitive: relies on imports appearing before exports in source order. Namespace imports (`import * as ns; export { ns }`) stay as local exports.
- **Class instance members**: `const svc = new MyService(); svc.greet()` and `this.service = new MyService(); this.service.doWork()` track the method as used. Chained `this.field` access uses synthetic `"this.field"` keys in `instance_binding_names`. Factory initializers through wrapper calls are also tracked: `const [svc] = useState(() => new MyService())` binds the first array-destructured element as an instance. Scope-unaware — false matches produce false negatives, not false positives.
- **Type-level member access**: `TSQualifiedName` (e.g., `type X = Status.Active`) tracked as member access. Mapped type constraints (`{ [K in Enum]: ... }`, `{ [K in keyof typeof Enum]: ... }`) and `Record<Enum, T>` mark all enum members as used via whole-object use.
- **TypeScript namespace exports**: `export namespace Foo { export function bar() {} }` extracts `Foo` as a single export with inner declarations as `NamespaceMember` entries, not as separate top-level exports. Runtime namespaces (no `declare`) are NOT type-only. `declare namespace`/`declare module` remain type-only. Nested namespaces flatten members into the outermost namespace.
- **Angular component metadata**: Full `@Component`/`@Directive` decorator metadata extraction prevents `unused-class-members` false positives. External templates (`templateUrl`) emit `SideEffect` imports and scan HTML for Angular syntax. Inline templates (`template:` string/template literals) are scanned in-place. `host:` object binding expressions extract referenced member identifiers. `inputs:`/`outputs:` string arrays mark listed members as framework-managed (handles `'name: alias'` syntax). Angular 17+ signal APIs (`input()`, `input.required()`, `output()`, `outputFromObservable()`, `model()`, `viewChild()`, `viewChildren()`, `contentChild()`, `contentChildren()`) set `has_decorator` on the property when the class has an Angular decorator. All template scanning supports `{{ }}`, `[prop]`, `(event)`, `[(ngModel)]`, `*ngIf`, `*ngFor`, `@if`, `@else if`, `@for`, `@switch`, `@defer (when expr)`, `@let name = expr;`, pipes. `*ngFor` and `@for` bindings are tracked as locals. `@let` variables are added as template-local bindings. `@defer` `when`/`prefetch when`/`hydrate when` conditions are scanned for member refs. **`inject(InjectionToken<Interface>)` external-template members** (issue #920): a field bound to an `InjectionToken` const (`readonly greeter = inject(GREETER)`, `GREETER = new InjectionToken<Greeter>(...)`) binds to the memberless token, not a class. Extraction records `new InjectionToken<I>(...)` from `@angular/core` as `(token, interface)` pairs on `ModuleInfo.injection_tokens` (CACHE_VERSION bumped; untyped tokens skipped, provenance-gated). The analyze bridge resolves the token export key (via `export_key_with_origins`) to its interface and credits the member on every class that `implements` it; the interface-typed field form (`x: Greeter = inject(TOKEN)`) treats the binding name as a candidate interface. Over-credits all implementers (safe false-negative direction), global-name matching, no provider parsing, external `templateUrl` only.

## Resolution-level
- **Package.json `exports` subpath**: output dirs (dist/build/out/esm/cjs) mapped back to src/ with source extension fallback, including nested subdirs
- **Pnpm virtual store**: `.pnpm` paths mapped back to workspace source files. Handles injected deps, scoped/unscoped packages, peer dependency suffixes.
- **Package.json `imports` (`#subpath`)**: simple mappings, wildcard patterns, conditional exports. Per-package scoping.
- **React Native platform extensions**: `.web.ts`, `.ios.ts`, `.android.ts`, `.native.ts` resolved alongside standard extensions
- **Web-root-relative paths**: `/src/main.tsx` or `/static/style.css` resolved as a web convention (Vite/Parcel/Hono). Converts to `./src/main.tsx` and resolves from the source file's parent directory first, then falls back to project root. This handles monorepo workspace members where `site/index.html` referencing `/src/main.tsx` resolves to `site/src/main.tsx`, not `<root>/src/main.tsx`. Applied to HTML, JSX, TSX, and JS/TS source files (extensions `.html`, `.jsx`, `.tsx`, `.js`, `.ts`, `.mjs`, `.cjs`, `.mts`, `.cts`). JSX/TSX support is needed for SSR frameworks like Hono where layout components emit `<link href="/static/style.css" />` from JSX templates. See issue #105 (till's comment).
- **CSS scoped package imports**: CSS `@import` with scoped npm packages (`@fontsource/monaspace-neon/400.css`, `@company/design-system/styles.css`) are kept as bare specifiers for node_modules resolution. Unscoped bare imports with CSS/SCSS extensions are normalized to relative paths (`app.css` becomes `./app.css`).
- **Tsconfig path aliases**: per-file discovery resolves `@/utils` by finding nearest tsconfig.json per file
- **Broken tsconfig chain fallback**: when `resolve_file` fails with a tsconfig-loading error (broken `extends` chain, circular extend, self-referencing project reference, malformed JSON, IO error), fall back to `resolve(dir, specifier)` which bypasses `TsconfigDiscovery::Auto`. A solution-style `tsconfig.json` with a broken sibling reference no longer poisons relative/bare-import resolution for files covered by a healthy sibling. A single `tracing::warn!` per unique error surfaces the broken chain to the user. Path aliases in the broken workspace remain unresolvable (they were already broken in `tsc`). See issue #97.
- **SCSS partial resolution**: `@use 'variables'` and `@import '../styles/variables'` resolve to `_variables.scss` per SCSS convention. Extensionless bare specifiers in `.scss`/`.sass` files (excluding `sass:*` built-ins) are normalized to relative paths at extraction time. Resolution fallback tries: (1) `_filename` partial prefix, (2) `specifier/_index` directory index, (3) `specifier/index` plain index. Prevents false unresolved-imports, unlisted-dependencies, and unused-files from SCSS partial references.
- **SCSS include paths**: framework plugins contribute absolute directories to `PluginResult.scss_include_paths`. The Angular plugin reads `projects.*.architect.build.options.stylePreprocessorOptions.includePaths` from `angular.json`; the Nx plugin reads the same key from `project.json`. Nx workspace tokens (`{projectRoot}`, `{workspaceRoot}`) in include paths are expanded before resolution: `{projectRoot}` is computed from the config file's parent relative to the workspace root, `{workspaceRoot}` is stripped (paths are already resolved from workspace root). See issues #103, #114. Bare SCSS specifiers that fail the file-local `try_scss_partial_fallback` retry against each include dir, applying `<name>`, `_<name>`, `<name>/_index`, `<name>/index` candidates. Only triggers for `.scss`/`.sass` importers and normalized bare specifiers (those prefixed with `./` at extraction time) — explicit parent-relative paths like `../shared/vars` are left alone.
- **SCSS node_modules resolution**: bare SCSS/Sass specifiers that fail both the local-partial and includePaths fallbacks are retried against `node_modules/` by walking up from the importing file to the filesystem root (matching Node.js / Sass semantics). `try_scss_node_modules_fallback` probes `<nm>/<pkg>/<path>.{scss,sass,css}`, `<nm>/<pkg>/<parent>/_<name>.{scss,sass}` (partial convention), and `<nm>/<pkg>/<path>/{_index,index}.{scss,sass}` (directory index). The CSS-extension append handles Sass's fallback for files like `animate.css/animate.min` → `animate.css/animate.min.css`. Because `node_modules/` files are outside fallow's file index (excluded by default ignore patterns), candidates are probed via `is_file()` on disk and a successful hit returns `ResolveResult::NpmPackage` (extracted via `extract_package_name_from_node_modules_path`), keeping `unused-dependencies` / `unlisted-dependencies` accurate. Scoped packages (`@scope/pkg/path`) are not prefixed with `./` by `normalize_css_import_path`, so they flow through `oxc_resolver`'s bare-module path directly and never reach this fallback. See issue #125.
- **CSS Modules class extraction skips `@layer` and `@import` preludes and records real source positions**: `extract_css_module_exports` runs `CSS_AT_RULE_PRELUDE_RE = @(?:layer|import)\b[^;{]*` after string and `url()` stripping and before the class regex, so dot-separated cascade-layer names (`@layer foo.bar { ... }`, `@layer foo.bar, foo.baz;`) and parenthesised layer references on `@import` (`@import url("x.css") layer(theme.button)`) never reach the class scan. Block bodies are preserved because the strip stops at the opening `{`; the allowlist is narrow so `@scope (.foo) to (.bar)` keeps real selector semantics. Every strip pass (block comments, SCSS line comments, quoted strings plus `url(...)`, the prelude strip) replaces matches with ASCII spaces of equal byte length so `CSS_CLASS_RE` capture offsets in the masked buffer index 1:1 back into the original source; each `ExportInfo` carries `Span::new(start, end)` pointing at the bare class identifier (no leading dot). Downstream `compute_line_offsets` resolves the real declaration line and column so LSP go-to-source, hover anchors, SARIF regions, and `--diff-file` line-overlap all land on the actual selector rather than line:1 col:0. Bumps `CACHE_VERSION` (89 to 90 for #540, 90 to 91 for #549). The function signature carries `is_scss: bool` so the SCSS-line-comment strip only fires for `.module.scss`. See issues #540 and #549.
- **Entry point source fallback for ignored output dirs**: when `package.json` `main`/`module`/`exports` resolves inside an output directory (`dist`, `build`, `out`, `esm`, `cjs`) and the direct `src/` mirror in `try_output_to_source_path` does not exist, `resolve_entry_path` probes `src/index.*`, `src/main.*`, `index.*`, `main.*` in the package root. Prevents the entire `src/` tree from becoming unreachable in libraries whose compiled entry (e.g. `dist/esm2022/index.js`) has no one-to-one source mirror. Emits a single `tracing::info!` per fallback. See issue #102.
- **Workspace package self-reference & cross-workspace fallback**: when a bare specifier's package name matches the root package or a workspace package and normal resolution either fails or lands inside `node_modules` for that same package, `try_workspace_package_fallback` first honors matching `package.json` `exports` entries and maps project-relative output targets (`dist`, `build`, `out`, `esm`, `cjs`) back to tracked source files. It then falls back to resolving the stripped subpath (`button`, `internal/base`, etc.) against a synthetic importer inside the package root, using `oxc_resolver`'s `resolve_file` so directory indices, source extensions, and the workspace's own `tsconfig.json` aliases still apply. Package `imports` (`#...`) use only the nearest owning package manifest, and unmatched hash aliases remain unresolved instead of becoming magical global aliases. Source-resolved package imports carry dependency usage metadata so static imports, dynamic literal imports, and re-exports keep `unused-dependencies` and `unlisted-dependencies` accurate. Handles Node.js v12+ self-referencing (`import '@org/pkg/sub'` from inside `@org/pkg`, common in Angular libraries built with `ng-packagr`), prebuild workspace `exports`, and Nitro-style package `imports`. See issues #106 and #641.
- **Iconify static icon strings credit `@iconify-json/<prefix>` packages**: icon components consume an icon set through a build-time string name (`<Icon name="jam:github" />`, `<List icon="ic:round-home" />`) rather than a JavaScript import, so the `@iconify-json/<prefix>` package supplying that collection was reported as an unused dependency. The extraction layer scans markup file kinds (`.astro`, `.jsx`, `.tsx`, `.svelte`, `.vue`, `.html`/`.htm`, `.mdx`) for static `icon=` / `name=` props whose value is `<prefix>:<name>` (HTML comments stripped first; capture is the collection prefix only) and records the deduped prefixes on `ModuleInfo.iconify_prefixes`. The analysis bridge (`crates/core/src/analyze/iconify.rs`) maps each prefix to `@iconify-json/<prefix>` and adds it to `referenced_dependencies`, GATED on the project declaring an Iconify-ecosystem dependency (`astro-icon`, `unplugin-icons`, `@iconify/*`, `@iconify-json/*`, `@iconify-icons/*`) across the root or any workspace `package.json`. Because the credit only exempts an already-declared package from the unused report and never creates a finding, a stray non-icon `name="foo:bar"` is harmless. Plain `.js`/`.ts` files, dynamic bindings (`:name=`, `name={expr}`), JSX brace-string form, and icon names referenced only from `.ts` data objects (`icon: "mdi:home"`) are out of scope. Bumps the extract `CACHE_VERSION` because the new `iconify_prefixes` field changes serialized module state. See issue #608.

## Graph-level
- **Type-only cycle filtering**: `import type` edges carry `is_type_only` through `ImportedSymbol` to cycle detection. Edges where all symbols are type-only are excluded from Tarjan's SCC successor list, preventing false circular dependency reports from type-only bidirectional imports.
- **`export *` chain propagation**: multi-level barrel file chains fully resolved for transitive usage tracking
- **CSS Modules**: default imports (`import styles from '...'`) resolve `styles.className` to named exports via graph-level narrowing. Spread/`Object.values` handled conservatively.

## Analysis-level
- **SvelteKit remote functions**: SvelteKit 2.27+ remote functions are exported from `*.remote.{ts,js}` files (`export const getPosts = query(...)`, plus `command` / `form` / `prerender`) and invoked through framework-generated client/server bindings that fallow's import graph cannot see. The SvelteKit plugin marks `src/**/*.remote.{ts,js}` as an entry pattern (so a generated-binding-only remote file is not reported as `unused-file`) and adds a `used_exports` rule mapping the same pattern to `["*"]` (so the user-named remote-function exports are credited and never report as `unused-export`, including under `--include-entry-exports` where the entry-point skip is disabled). Remote-function export names are user-defined, so a fixed convention list cannot enumerate them; `"*"` is the conservative credit, mirroring the Storybook story-file precedent. Import edges for dependencies referenced inside remote files are preserved because the file is parsed as an entry point. Scoping is by the `.remote.` double-extension only, so ordinary `src/**/*.ts` files (and a genuinely-unused non-remote module) stay governed by normal detection; `src/lib/server/**` is not excluded because SvelteKit forbids remote files there and crediting a stray one is harmless. See issue #611.
- **SvelteKit layout-reset routes**: SvelteKit's layout-reset convention appends an `@` suffix to a page or layout component to break it out of its parent layout chain (`+page@.svelte` resets to the root layout, `+page@named.svelte` resets to a named layout). The SvelteKit plugin marks `src/routes/**/+page@*.svelte` and `src/routes/**/+layout@*.svelte` as entry patterns and adds `used_exports` rules crediting their `default` export, so layout-reset routes stop reporting as `unused-file` and their component default stays credited. The `*` covers both the empty (`@.svelte`) and named (`@named.svelte`) forms; `literal_separator(true)` keeps the glob within a single path segment. Only `.svelte` component files take the suffix: SvelteKit itself throws on `@` in `.ts`/`.js` route files (`+page@.ts` is invalid), and `+error.svelte` / `+server.{ts,js}` have no `@` variant, so no module-file or error/server patterns are added. See issue #791.
- **electron-vite `rollupOptions.input` entries**: the Electron plugin activates on `electron` / `electron-builder` / `@electron-forge/cli` / `electron-vite`. When `electron.vite.config.{ts,js,mjs}` is present it parses each of the `main` / `preload` / `renderer` sections' `build.rollupOptions.input` (string, array, and object-of-values forms) and seeds each value as an entry point, normalized relative to the config file via `normalize_config_path`. Object values commonly use path helpers (`resolve(__dirname, 'src/renderer/index.html')`, `join(...)`, `fileURLToPath(...)`, `new URL(..., import.meta.url)`); the shared `config_parser::extract_config_string_or_array` evaluates those through `expression_to_path_string` (broadened in issue #604), so the Electron plugin reuses it directly rather than carrying its own extractor. Renderer HTML entries become entry points, so the `<script src>` source trees behind multi-window renderers stop reporting as `unused-files`. The static main/preload fallback globs also widen to `{ts,tsx,js,jsx,mts,mjs}`. Crediting is scoped to declared inputs (per-section function-wrapped configs are out of scope), so a renderer source file linked from no declared entry is still reported. See issue #600.
- **Browser extension manifest entrypoints**: the `browser-extension` plugin activates without package dependencies by inspecting deduped `manifest.json` candidates at the project root and discovered-file ancestor directories. Activation requires numeric `manifest_version` 2 or 3 plus at least one extension runtime key (`background`, `content_scripts`, action/page/browser action, options, side panel, devtools, or `web_accessible_resources`) so ordinary PWA manifests stay inert. Config resolution seeds MV3 `background.service_worker`, MV2 `background.scripts`, `content_scripts[].js/css`, popup/options/devtools/side-panel HTML, MV2 string-array `web_accessible_resources`, and MV3 object `resources` arrays as runtime entry patterns, normalized relative to the manifest file. Remote/scheme URLs, protocol-relative URLs, empty strings, and parent-directory escapes are skipped; leading `/foo.js` is treated as extension-root-relative. HTML entries rely on the existing HTML asset extractor to keep their `<script>` and stylesheet graph reachable. See issue #616.
- **WXT entrypoints and config modules**: the `wxt` plugin activates from `wxt`, any non-empty `@wxt-dev/*` dependency, or a root `wxt.config.{ts,js,mts,mjs,cjs,cts}` file. It keeps WXT config files always used, credits their default export under `--include-entry-exports`, marks documented single-file `entrypoints/*` and directory `entrypoints/**/index.*` entrypoints (plus `src/entrypoints` variants) as runtime roots, and parses static `modules: [...]` strings from config as referenced dependencies. Package subpaths are normalized (`@wxt-dev/i18n/module` credits `@wxt-dev/i18n`); local, absolute, protocol, empty, and backslash-containing specifiers are ignored. The entry globs intentionally do not credit every descendant under an entrypoint directory, so unimported helper siblings stay reportable. See issue #612.
- **Code duplication atomic-call filter**: duplication tokenization records spans for `CallExpression` / `NewExpression` clones and return/await/expression-statement wrappers around them when the invocation has no direct arrow/function-expression argument. Clone groups whose every instance fits entirely inside one of those atomic invocation spans are filtered before group construction, because the shared abstraction is already the callee and `extract-shared` would usually suggest wrapping a call in another function. Callback-style calls stay eligible so repeated route handlers, hooks, and other copied callback bodies still report normally. See discussion #320.
- **Duplicate export common-importer filter**: duplicate exports are only reported when at least two files sharing the same export name also share a common importer in the module graph. Unrelated leaf files (e.g., SvelteKit route modules in different directories) that coincidentally export the same name are not flagged.
- **Decorated class members**: members with decorators (NestJS `@Get()`, Angular `@Input()`, TypeORM `@Column()`) not reported unused
- **Typed instance chains**: class-member usage propagates through non-private typed constructor parameters, typed properties, and typed getters. A call such as `factory.service.query()` credits `Service.query` when `factory` is a `Factory` instance and `Factory.service` is declared as `Service`; reflective whole-object uses such as `Object.keys(factory.service)` mark the target service whole-object used through the same chain. This includes getter-backed factories used inside Playwright fixture teardown blocks.
- **Configurable class member allowlist**: the built-in Angular/React lifecycle check (see `predicates::lifecycle`) is extended at analysis time with two user-controlled sources: (1) top-level `FallowConfig.used_class_members`, (2) `Plugin::used_class_members()` / `ExternalPluginDef.used_class_members` on active plugins. Both sources feed `AggregatedPluginResult.used_class_members`, which `analyze/mod.rs` merges with the config list into a single `FxHashSet<&str>` passed to `find_unused_members`. Intended for third-party interface patterns where a library calls consumer methods reflectively (ag-Grid's `agInit`/`refresh`, Web Components' `connectedCallback`). The allowlist is scoped to class members — matching enum member names are still flagged. See issue #98.
- **Inheritance-aware class members**: `extends` clauses are extracted to build an inheritance map. Parent class `this.*` accesses propagate to child class overrides (e.g., `BaseShape.describe()` calling `this.getArea()` credits `Circle.getArea()`). External member accesses propagate bidirectionally through the hierarchy. Only simple identifier extends are tracked (`class Foo extends Bar`), not mixin patterns. Methods called through parent-typed parameters remain unattributed (requires type inference, out of scope per ADR-001).
- **JSDoc visibility tags** (`@public`, `@internal`, `@beta`, `@alpha`, `@expected-unused`): exports annotated with any of these JSDoc/TSDoc tags are never reported as unused. Stored as a `VisibilityTag` enum on `ExportInfo` and `ExportSymbol`, preserving the semantic distinction (Public = API surface, Internal = sister packages/build tools, Alpha = early preview, Beta = unstable, ExpectedUnused = intentionally unused). Priority when multiple tags present: Public > Internal > Alpha > Beta > ExpectedUnused. Only `/** */` block JSDoc comments recognized. `@api public` TSDoc variant also supported. Word-boundary checked (e.g., `@internalizer` does not match). Survives incremental cache roundtrip via `u8` discriminant encoding. `@expected-unused` differs from other tags: when the tagged export IS actually used (has references from reachable modules), a stale suppression is reported instead of silently accepting it. This supports the pattern of marking API-completeness exports that become adopted over time.
- **Same-file value references and unused exports**: `unused-export` reports public export surface, not whether the local declaration is needed by another declaration in the same module. A value that is only referenced by another same-file export, for example `export const child = ...; export const parent = use(child);`, still reports as an unused export unless it has a reachable cross-file reference, a visibility tag such as `@public`, an `ignoreExports` rule, or `ignoreExportsUsedInFile` enabled. The generated fix action removes only the export modifier and leaves the local value available to `parent`. This keeps `dead-code`, `trace`, and stale suppression consumption aligned for local-only helpers and schema constants.
- **Stale suppression detection**: after all detectors run, `SuppressionContext` compares consumed vs. all suppression comments. Unmatched `// fallow-ignore-next-line` and `// fallow-ignore-file` comments are reported as stale. Default severity: `Warn`. CLI-side suppression kinds (complexity, coverage-gaps, feature-flag, code-duplication) are excluded from stale detection to avoid false positives, since their suppression checks run in the CLI layer, not in `find_dead_code_full`. **Suppressions for disabled rules** (`rules.<kind> == "off"`, including per-file `overrides.rules`) **are NOT reported as stale** (issue #482). `SuppressionContext::find_stale` resolves rules once per file via `ResolvedConfig::resolve_rules_for_path` and skips emission when the suppression's target kind has severity `Off`. The suppression documents intentional dormancy and becomes valid again when the rule is re-enabled. Blanket markers (`// fallow-ignore-next-line` with no kind) are not anchored to any specific dormant kind, so they still surface as stale when nothing matches. The `Suppression` struct stores `comment_line: u32` alongside the target `line: u32` so stale reports point at the comment itself, not the suppressed line. `@expected-unused` JSDoc tags produce stale entries via the unused export detector when the tagged export becomes used. Both comment and JSDoc tag stale entries feed into the same `stale_suppressions` vec on `AnalysisResults` with a discriminated `SuppressionOrigin` enum.
- **Arrow-wrapped dynamic imports**: `React.lazy(() => import('./Foo'))`, `loadable(() => import('./Component'))`, `defineAsyncComponent(() => import('./View'))`, and any function call with an arrow or function expression argument whose body is a sole `import()` expression. The default export of the target module is credited as used (lazy loading wrappers always consume the default export). Handles expression body (`() => import('./x')`), block body (`() => { return import('./x'); }`), and function expressions (`function() { return import('./x'); }`). The import span is added to `handled_import_spans` to prevent duplicate side-effect edges from the generic `visit_import_expression` walker.
- **Dynamic import `.then()` callback**: `import('./lib').then(m => m.foo)` tracks `foo` as a named import from `./lib`. The standard Angular lazy-loading pattern (`loadComponent: () => import('./x').then(m => m.Component)`). Three sub-patterns: (1) expression body member access (`m => m.foo`) extracts specific member names as `destructured_names`, (2) destructured parameter (`({ foo, bar }) => { ... }`) extracts names from the object pattern, (3) identifier parameter with block body (`m => { ... }`) registers as a namespace binding for member-access narrowing. Also handles `({ default: m.Foo })` object literal bodies (React.lazy `.then` pattern) and function expression callbacks. The import span is added to `handled_import_spans` to prevent duplicate side-effect edges. See issue #115.
- **Infrastructure entry points**: Dockerfiles, Procfiles, fly.toml scanned for source file refs. Searches root and config/docker/deploy subdirs.
- **TypeScript project references**: tsconfig.json `references` field discovered as workspaces (additive with npm/pnpm workspaces)
- **CI file scanning**: `.gitlab-ci.yml` and `.github/workflows/*.yml` scanned for binary invocations (npx, direct binaries) AND positional file arguments (`node scripts/deploy.ts`, `--config foo.cjs`). Binary names map to npm packages (CI-only deps stay flagged-as-used); file-path arguments are seeded as project-relative entry patterns so scripts invoked only from CI are not reported as `unused-files` (issue #195 Case D). Line-based YAML parser; known limitations: variable interpolation (`${{ matrix.env }}/deploy.ts`), `\` line-continuations, and YAML anchors (`<<: *defaults`) are silently skipped.
- **Production mode**: excludes test/dev files, only start/build scripts, skips unused devDeps, detects type-only deps. Config file exclusion (`*.config.*`) is root-anchored only; nested `*.config.*` files (e.g., Angular's `src/app/app.config.ts`) are preserved. All production exclude globs use `literal_separator(true)` so `*` cannot cross path separators. See issue #111.
- **Test-only dependency detection**: `find_test_only_dependencies` identifies production dependencies imported exclusively from test/dev/config files (should be devDependencies). Uses a dual classification: glob patterns from `PRODUCTION_EXCLUDE_PATTERNS` for test/story files (`**/*.test.*`, `**/*.spec.*`, `**/__tests__/**`, etc.) and the curated `is_config_file()` predicate for tooling config files at any depth. The predicate approach avoids false matches on application config files like `app.config.ts` while correctly matching workspace-level configs like `packages/foo/vitest.config.ts`. See issues #111, #112.
- **Peer dependency credit**: unused dependency detection reads `peerDependencies` from installed packages under `node_modules/`. When a package is used by the module graph, its required peer dependencies are treated as used too, recursively. Peers marked with `peerDependenciesMeta.<name>.optional: true` are not credited. Package lookup walks from the current package or workspace root through ancestor directories, so hoisted and workspace-local installs are both covered. The peer graph is cached per analysis run and only expands from packages already used by source imports. See issue #199.
- **Platform built-in modules**: `node:`, `bun:`, `cloudflare:`, `sass:` prefixed imports and Deno `std` are recognized as builtins — never flagged as unlisted dependencies. The `sass:` prefix covers the Sass compiler's built-in modules (`sass:math`, `sass:string`, `sass:color`, `sass:list`, `sass:map`, `sass:meta`, `sass:selector`) imported via SCSS `@use 'sass:math'`. See issue #104.
- **`ignoreDependencies` dual suppression**: listed packages are excluded from both unused dependency AND unlisted dependency detection, making it useful for runtime-provided packages (e.g., `bun:sqlite`).
- **`ignoreUnresolvedImports` raw specifier suppression**: listed glob patterns suppress only `unresolved-import` findings whose raw import specifier matches. They do not affect dependency usage or resolver behavior. `@example/icons/**` matches subpaths but not the bare `@example/icons`, so users must list both when both are expected; parent-relative generated specifiers such as `../generated/**` are valid because the field is not a filesystem glob. Broad patterns such as `**` can hide real missing modules. See issue #726.
- **@types/ unlisted dep suppression**: imports from `pkg` not flagged as unlisted when `@types/pkg` is in deps (TypeScript resolves types from `@types/` and erases the import regardless of `import type` syntax). Scoped packages use DefinitelyTyped convention (`@scope/pkg` → `@types/scope__pkg`).
- **Architecture boundary violations**: user-defined zones (glob patterns) with directional import rules. Fires at direct import site using resolved target's zone. Unzoned files are unrestricted in both directions. First-match zone classification. Self-imports always allowed. Inline and file-level suppression supported. `autoDiscover` on a zone scans immediate child directories and creates child zones named `parent/child`; rules that reference the logical parent expand to all discovered child zones. If the parent also has patterns, discovered children are ordered before the parent fallback, and the parent fallback rule automatically allows its discovered children so top-level barrels can re-export them without relaxing generated child rules. Built-in presets: `layered` (presentation/application/domain/infrastructure), `hexagonal` (adapters/ports/domain), `feature-sliced` (app/pages/widgets/features/entities/shared), `bulletproof` (app/features/shared/server — features auto-discover child modules; shared zone covers components, hooks, lib, utils, utilities, providers, shared, types, styles, i18n). Presets auto-detect `rootDir` from tsconfig.json for pattern prefix. User zones/rules merge on top of presets (same-name replaces). Zones with zero file matches emit warnings.
- **Static test coverage gaps**: module graph reachability from test entry points to runtime files/exports. Not line-level coverage. Test files are identified by plugin patterns and production-mode exclusion rules. Reports runtime files with no test dependency path and runtime exports with no test-reachable reference chain. Gated by `--coverage-gaps` flag on the health command and `coverage-gaps` rule severity.
- **Complexity suppression**: health command complexity findings (functions and synthetic Angular template entries exceeding cyclomatic/cognitive thresholds) support inline suppression via `// fallow-ignore-next-line complexity` and `// fallow-ignore-file complexity`. The blanket `// fallow-ignore-next-line` (no kind) also suppresses complexity findings on the next line. The check happens in `collect_findings()` in `crates/cli/src/health/mod.rs` using `suppress::is_suppressed()` with `IssueKind::Complexity` (discriminant 18). File scores and vital signs are NOT affected by suppressions (they reflect actual complexity, not alerting). Synthetic Angular `<template>` findings in `.html` files get file-level suppression actions because line comments cannot be expressed in HTML; inline template findings in `.ts` files keep line-level suppression actions anchored at the decorator. Synthetic `<template>` findings in `.svelte`, `.vue`, and `.astro` single-file components get line-level suppression actions with the markup comment `<!-- fallow-ignore-next-line complexity -->` on the line immediately above the reported line (`placement: "above-template-anchor-line"`); the template unit anchors at its first contributing construct, not the top of the file (issue #2163). See issue #108 (till's comment).
- **Script binary-to-package resolution**: npm `scripts` binary names are mapped to package names via a 4-step chain: (1) static `BINARY_TO_PACKAGE` table for known divergences (`tsc` -> `typescript`, `ng` -> `@angular/cli`, etc.), (2) `node_modules/.bin/<binary>` symlink target path extraction, (3) dynamic reverse map built from each dependency's `package.json` `bin` field (handles both string `"bin": "./cli.js"` and object `"bin": {"attw": "./cli.js"}` forms), (4) identity fallback (binary = package name). The dynamic map probes `node_modules/` at both the project root and each workspace root, handling non-hoisted setups (pnpm strict, Yarn workspaces). Built once per analysis run. See discussion #107. Positional file arguments (`tsc ./scripts/deploy.ts`, `node ./scripts/deploy.js`) extracted from script values are seeded as entry patterns to keep CI-only / deploy-only sources reachable. Extensionless script file paths also probe `entry/index.*` after exact-file and source-extension fallback, matching Node directory entry behavior for script shapes like `node scripts/process-messages`. For workspace packages, paths are joined with the workspace's project-relative prefix and `..` segments are normalized via `normalize_script_entry_pattern`; `..` segments that escape the project root are skipped instead of producing unmatchable globs (issues #195 Case C and #638). `bun` is handled as both a script runner and a direct executor: leading boolean runtime flags (`--bun`, `--watch`, `--hot`, `--smol`, `--no-clear-screen` in `BUN_RUNTIME_FLAGS`) are skipped so `bun --bun prek install` extracts and credits the `prek` binary (resolving `prek` -> `@j178/prek` through the dynamic bin map), while `bun --watch run dev`, bare `bun <script>`, and any unrecognized leading flag still resolve to script delegations (conservative: an unknown flag may take a value, so it is never guessed at). `bun x <pkg>` is treated as the bun-native alias of `bunx`. See issue #755.
- **Vite `css.preprocessorOptions.{scss,sass,less,stylus}.additionalData`**: the Vite plugin extracts the string value at each preprocessor's `additionalData` key from `vite.config.{ts,js}` and scans it for stylesheet imports via the same regex used by the CSS file parser. SCSS / Sass bodies seed discovered local style paths as entry patterns and use SCSS-aware normalization (extensionless local specifiers become `./X` partials); package imports such as `bootstrap` and `bootstrap/scss/functions` are credited as referenced dependencies instead of inert entry globs when no matching local style candidate exists. Less / Stylus strings are parsed for `@import "path"` and package dependency credit, but local `.less` / `.stylus` files are not currently part of the discovered source-file set. Function-form `additionalData: (source, file) => ...` is silently skipped (out of static-analysis scope). Specifiers are stripped of leading `./` before push because globset matches against project-relative paths without that prefix. See issue #195 Case A.
- **Cypress `e2e.specPattern` / `component.specPattern` / `supportFile`**: the Cypress plugin reads `cypress.config.{ts,js,mjs,cjs}` and seeds `e2e.specPattern`, `component.specPattern`, `e2e.supportFile`, and `component.supportFile` (string or array of glob patterns / paths) as entry patterns. Static patterns under `**/*.cy.{ts,tsx,js,jsx}`, `cypress/**/*.{ts,tsx,js,jsx}`, and `cypress/support/**/*.{ts,js}` seed Cypress's default component spec discovery and default Cypress 9-style layout; the config-driven extraction handles Cypress 10+ projects whose specs live outside `cypress/` (e.g. `tests/**/*.cy.ts`, `src/**/*.cy.ts`). See issue #195 Case E.
- **Script multiplexer handling**: `concurrently`, `npm-run-all`, `npm-run-all2`, `run-s`, `run-p`, `run-s2`, `run-p2` are recognized as script multiplexers. Their positional arguments are treated as script names (not binary names or file paths) and excluded from `used_packages`. Only the multiplexer binary itself is recorded. This prevents false "unused dependency" reports for packages referenced only via `npm:` prefixed script delegation (e.g., `concurrently "npm:dev" "npm:test"`).
- **Entry export validation** (`--include-entry-exports`): when enabled, entry file exports (package.json main/module/exports, framework convention files) are subject to unused-export detection instead of being automatically marked as used. Catches typos in framework exports (e.g., `meatdata` instead of `metadata` in Next.js pages). Still respects plugin `used_exports` rules for partial checking. CLI-only flag, not in config schema.
- **Single-file filtering** (`--file`): scopes check output to specified file(s). Full graph still builds (correct results require cross-file analysis), but only issues in matching files are reported. Dependency-level issues (unused deps, dev deps, type-only deps) are suppressed in file mode since they are project-wide properties. Warns when a path is not found. Useful for lint-staged pre-commit hooks.
- **Feature flag detection**: AST-based detection of feature flag patterns. Three categories: (1) environment variables (`process.env.FEATURE_*` with 12 built-in prefixes), (2) SDK calls (25+ built-in patterns for LaunchDarkly, Statsig, Unleash, GrowthBook, Split, ConfigCat, Flagsmith), (3) config objects (opt-in heuristic for objects named "feature", "flag", "toggle"). Reports flag locations, detection confidence (high/low), guard spans. Cross-references with dead code: flags guarding unused exports are highlighted. Configured via `flags` section in config. Default severity: `off`. CLI: `fallow flags`. Inline suppression: `// fallow-ignore-next-line feature-flag` (line-level) and `// fallow-ignore-file feature-flag` (file-level). The suppression check runs in `crates/cli/src/flags.rs` during both built-in and custom flag collection loops, using `is_suppressed()` / `is_file_suppressed()` with `IssueKind::FeatureFlag`. The file-level check is hoisted outside the per-flag loop for efficiency.
- **Client-server-leak security candidates** (opt-in, `fallow security` only): graph-structural rule that flags a `"use client"` file whose transitive static-import cone reaches a module that reads a non-public `process.env` secret, plus the direct case where the client file reads such a secret itself. Findings are candidates for downstream agent verification, not verified vulnerabilities; there is no `confidence` or `signal_strength` field, only the structural import-hop `trace`. Implemented in `crates/core/src/analyze/security/mod.rs`: file-level directive capture (`ModuleInfo.directives`, captured by the extract visitor; `CACHE_VERSION` bumped to 106) identifies client boundaries; secret sources are detected from existing `member_accesses` (`process.env.X` surfaces as `MemberAccess { object: "process.env", member: "X" }`), excluding public-by-convention prefixes (`NODE_ENV`, `NEXT_PUBLIC_`, `VITE_`, `NUXT_PUBLIC_`, `REACT_APP_`, `PUBLIC_`, `GATSBY_`, `EXPO_PUBLIC_`, `STORYBOOK_`); the reachability BFS skips type-only edges. The rule defaults to `off`, and `fallow security` forces it to `warn`. Findings live on `AnalysisResults.security_findings` (`#[serde(skip)]`, excluded from `total_issues`), so they never appear under bare `fallow` or the `audit` gate. Dynamic `import()` patterns the BFS cannot follow bump `security_unresolved_edge_files`; `import.meta.env` is not modeled. Inline suppression: `// fallow-ignore-file security-client-server-leak`, routed through `SuppressionContext::is_file_suppressed` so the marker is consumed and not later flagged stale. Each finding carries an `actions` array with that file-level suppress hint (`auto_fixable: false`).
- **Data-driven tainted-sink source backing** (opt-in, `fallow security` only): `SinkSite.arg_idents` and `SinkSite.arg_source_paths` let the `tainted_sink` detector raise ranking when a sink argument traces to a catalogue `[[source]]` path. `ModuleInfo.tainted_bindings` records direct source bindings such as `const id = req.query.id`, destructures such as `const { id } = req.query`, direct source expressions in sink arguments, and issue #878's one-hop same-module helper returns such as `const id = getUserId(req)` when `getUserId(request)` returns `request.query.id`. This remains ranking and evidence only: it never gates a sink finding in or out, never crosses modules, never follows helper aliases, and never follows helper-to-helper chains. `CACHE_VERSION` was bumped to 111 for the original source model and to 131 for #878 helper-return propagation.
- **Complexity contribution breakdown** (`--complexity-breakdown`): `ComplexityVisitor` (`crates/extract/src/complexity.rs`) records one `ComplexityContribution { line, col, metric, kind, weight, nesting }` per increment event during the existing single AST pass, on `FunctionComplexity.contributions` (cached; `CACHE_VERSION` 117), surfaced on `ComplexityViolation.contributions` in `health --format json` only with `--complexity-breakdown` (gated at population via `contributions_for`; omitted via `skip_serializing_if`). The inc_* helpers fuse record-and-increment so the breakdown reconstructs the aggregate; the else-if path was refactored to a flat `+1` (`ElseIf`), metric-neutral (byte-identical OLD-vs-NEW). React JSX depth is descriptive `react_jsx_max_depth` context only, so current extraction does not emit `jsx-depth` entries. VS Code renders it inline; MCP `check_health` exposes `complexity_breakdown`.
